# MeshCore 1.17.1.9 USA Cascade

This release remains held and unpublished.

USA Cascade defaults are 910.525 MHz, 62.5 kHz bandwidth, SF7 and CR5. Saved
radio settings take precedence. Match the exact board, role and storage
layout before installing an image.

## Changes since 1.17.1.8

- ESP32 native USB recipes now use hardware CDC where the chip supports it.
  Classic ESP32 and explicit UART transports keep their UART path. nRF52,
  RP2040 and STM32 USB backends are unchanged by this migration.
- Heltec V4 and V4 R8 user buttons wake CPU light sleep when power saving is
  enabled. Button debounce and click deadlines remain awake so the display can
  process the press. Explicit display-off mode still suppresses screen wake.
- ESP32 USB output is bounded so a stopped reader cannot indefinitely hold
  the radio loop. The G2 preserves complete serial packet-log lines under
  congestion. This supports unmodified Cisien meshcoretomqtt; congested
  diagnostic output can still be dropped.
- The pinned ESP32-S3 framework releases retained TinyUSB PHY ownership when
  starting hardware CDC after a software restart. KISS clears incomplete
  host frames on a USB session reset while preserving active radio work.
- Browser OTA uploads allow 30 seconds of body inactivity after admission.
  An upload error stays attached to its HTTP request and stops further flash
  writes. Error callbacks avoid raw USB printing that could block the shared
  network task when a connected host stops reading.
- Infrastructure WebConfig retries its saved WiFi when MQTT has no running
  worker. Ownership follows the actual worker state while canonical WiFi
  credentials and 64-hex password support remain independent of that state.
  Companion's manual WiFi startup behavior is preserved.
- Companion packet streaming supports stock serial MQTT consumers. Text CLI
  and Binary Companion handoff and reply deadlines are covered against the
  official app's protocol behavior.
- Access Control replies fit the encrypted LoRa route budget and the
  Companion frame envelope. Large ACL listings use bounded pages. ESP32 ACL
  persistence avoids repeated metadata opens while retaining recovery checks.
- Companion requests skip recently used reply tags. A login reply whose
  server timestamp matches the next client timestamp no longer causes an
  immediate status or ACL request to fail locally. Stale replies remain
  blocked, and tag selection does not change the radio's wall clock.
- nRF52 keeps its 8 KiB loop stack. Crypto, contact CRC and background storage
  work reduce peak stack use and long pauses. OTA metadata is cached after
  verification instead of repeatedly reopening storage for status displays.
- T096 and T1 repeater profiles reserve four flood-rule entries to fit the
  complete sensor profile with the existing 8 KiB loop stack, 50 neighbors,
  color framebuffer and OTA arena. Their capability manifests record this
  capacity limit; heap qualification margins are unchanged.
- The RAK3401 unified repeater reserves 47 flood-rule entries so its full
  sensor profile, 8 KiB loop stack, 50 neighbors and internal/QSPI OTA stores
  fit the runtime RAM requirement. Full and reduced sensor images use the
  same table capacity; the capability reports record this limit.
- Flood-policy upgrades accept inactive trailing rows from larger tables.
  If active rules exceed an image's capacity, the stored file is preserved and
  policy saves are blocked. The CLI reports the capacity mismatch; install
  firmware with enough rule slots to recover the complete policy.
- ESP32 filesystem buffer checks cover the pinned Arduino 3 frameworks used
  by RC32 and C6 targets and continue rejecting unhonored buffer allocations.
- Generic ESP-NOW Full Companion retains all Full transports and 100 contacts
  with a 224-frame offline queue to meet the unchanged runtime RAM requirement.
- Wio-E5 Mini Companion uses smaller generated code while preserving its
  filesystem allocation, contacts, channels and physical-button controls.
  CI compiles its actual Cascade release profile with the full version string.
- Mesh America preserves download-only installation for hardware cards that
  require it, including their Full and reduced sensor profiles.

## Installation

An ESP32 merged `.bin` installs bootloader, partitions and application over
USB. An app-only `.bin` requires a compatible existing layout. Partition
expansion requires the exact board and role migration ZIP from this release
family's utility page, or the matching merged image over USB. Follow the ZIP's
README and use its supplied Full application. `get storage.layout` reports
the live layout on firmware that supports it.

Check the image's flood-rule capacity before updating a repeater. Move active
rules into the supported slots and save them before installing a smaller
table. An over-capacity policy is retained on storage but remains inactive
until compatible firmware is installed.

Switching from TinyUSB to native hardware CDC changes the USB product name and
Linux `/dev/serial/by-id` path. Update serial consumers to the new device path
after the first upgrade.
Hardware CDC descriptors are fixed in silicon; firmware cannot retain a custom
TinyUSB product name. Do not identify a radio solely by a changing `/dev/ttyACM`
number. See [Espressif's explanation](https://github.com/espressif/arduino-esp32/issues/11394#issuecomment-3778833461).

nRF52 application UF2 and DFU ZIP files do not install a bootloader. Use the
exact board/storage OTAFIX mapping in the [firmware picker](../firmware_picker.md).
See the [role controls](../role_feature_switches.md),
[Full Companion guide](../full_companion_features.md), and
[USB web console](https://flasher.meshcore.io/console).

## Verification scope

The ESP32 migration passed the native unit suite, SDK and protocol regression
tests, sanitizer fixtures and representative builds across all affected board
families. The G2 passed physical USB command/reconnect tests with its original
identity and settings preserved. A separate RAK4631 recovery admin was verified
by passwordless LoRa login, remote status and a remote version reply.

Earlier old-firmware handoff attempts did not qualify an OTA migration. After
USB restoration, hardware CDC passed 444 strict-deadline queries and a
150-second closed-port idle/reconnect test. Those results remain separate from
the subsequent physical OTA qualification.

On 2026-10-05, the G2 passed an app-only HTTP OTA upgrade from a real TinyUSB
build to normal hardware CDC, both built from `95913c53`. The test drained the
same TCP socket's outstanding bytes before pausing the upload for 4.510 seconds.
HTTP returned 200 after 22.559 seconds. Firmware restarted itself, the host
observed the USB product change, and the first ordinary website `time` command
was acknowledged in 2.997 seconds against the unchanged 5-second deadline.
Identity, saved runtime settings, and the original and recovery Admin ACLs
were preserved. No cable, power, reset, ROM or rescue action was used during
the measured upgrade; the Pi's original WiFi connection was restored.

This is a controlled current-source TinyUSB baseline, not proof of an upgrade
from released stock 1.17.1. A separate earlier LAN upload reset mid-transfer;
continuous uptime and a later successful AP retry showed no CPU crash, but
the LAN failure's cause remains unproven. The synthetic regressions execute
production upload callbacks, preserve queued errors, and distinguish the old
3-second body timeout from the bounded 30-second allowance. Local uploader,
OTA startup, WiFi lifecycle and station ownership tests passed. The latest
`95913c53` hardware CDC application passed quiet 180-second power-saving trials
with the port open and closed, without keepalives or a CPU restart. First
replies took 18.551 ms and 14.728 ms; original power-saving off and other saved
settings were restored. A plain `start ota` then advertised a working LAN
endpoint, reported the WebConfig handoff, and served its page and exact G2
identity over HTTP. OTA stopped cleanly and the original WebConfig, settings,
Admin ACLs, Pi network and host services were restored. The earlier radio CAD
warning remained unchanged; the earlier LAN upload failure's cause is still
unproven. The GitHub unit workflow passed for source `c88885a3`; this release
remains held and unpublished.

The normal Full Heltec V4 Repeater from `c88885a3` passed two fresh-flash
connections through the unchanged native Chromium setup GUI. With power saving
on, its quiet console checks passed for 600 seconds open and closed with logging
off, and 600 seconds open with USB logging. See the [V4 native console
qualification](../test-results/hardware_validation_heltec_v4_native_console_2026-10-06.md)
for deadlines, host preparation and retained failed attempts. USB remained
attached, so these checks do not measure CPU sleep or button wake. The subsequent
`ebf2f082` V4 button-wake profile correction passed host tests and linked-image
checks, followed by another unchanged native GUI fresh-flash connection and
180-second open/closed console checks with power saving on and USB logging.
Original settings, identity and ACL response were restored. Physical button
wake, CPU sleep and current draw were not tested here; the new source's GitHub
unit workflow remains in progress.

Build qualification does not establish physical compatibility on every board.
Hardware CDC has finite buffers, and closing a Linux TTY does not necessarily
produce a hardware session reset. Saturated diagnostic output is not lossless.
See [USB backpressure test results](../test-results/usb_serial_backpressure.md)
for measured scope and the upstream issues reviewed.
